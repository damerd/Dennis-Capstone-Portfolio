Artifact Description

ClaimIntel is an AI-assisted insurance claims intelligence application that I built in 2026 to help organize and evaluate complex property and casualty claim files. The idea grew out of work I completed in CS 360, but it quickly became a larger personal project because it allowed me to connect what I was learning in computer science with my professional experience in commercial claims, litigation management, and claims leadership. Users can enter claim information, upload documents, and generate a structured report that addresses areas such as liability, coverage, damages, venue, exposure, missing evidence, and recommended next steps.

Before this enhancement, ClaimIntel could already save and retrieve claim reviews through Base44, but the data structure still reflected an early beta version of the application. Almost everything was stored in one large ClaimReview entity, including the basic claim information, source text, AI-generated sections, readiness data, validation results, and comparative-verdict information. Several screens also communicated with the database directly. The application worked, but the design was becoming harder to maintain. Records were growing larger, the interface was too closely tied to the persistence layer, and there was no practical way to restore a deleted record or review how it had changed over time.

I chose ClaimIntel for the database category because the problem went beyond adding another feature. The original design limited how useful the application could become over time. My long-term goal is for ClaimIntel to support repeat reviews, historical claim intelligence, auditing, and eventually organizational learning. To move in that direction, the application needed a better way to separate different types of information, preserve relationships between records, control how data is retrieved and updated, and protect sensitive insurance information.

Justification for Inclusion and Enhancement

ClaimIntel is a strong fit for my ePortfolio because it shows how I can take a real industry problem and turn it into a working computing solution. A basic database assignment could demonstrate that I understand records and CRUD operations, but this project shows how those concepts apply in an actual claims environment. Claim systems have to manage parties, policy information, uploaded documents, medical and financial details, analytical reports, status changes, and user activity. They also need a dependable history because decisions may be reviewed months or even years later. This enhancement allowed me to show both the technical side of database design and the practical reasons behind those decisions.

The biggest architectural change was moving away from a page-centered persistence model and toward a related-entity design supported by repositories and a compatibility adapter. I added ClaimAnalysis, ClaimDocument, and ClaimReviewHistory while keeping ClaimReview as the main claim record and AuditLog as the operational audit record. Each related entity uses the ClaimReview identifier to connect back to the parent claim. Base44 manages the underlying database for the application, so these are logical application-level relationships rather than traditional SQL foreign-key constraints. I felt it was important to explain that limitation clearly instead of claiming the platform provides controls that it does not expose.

The updated ClaimReview entity now focuses on the information that defines and tracks the claim itself. I added a normalized claim number, lifecycle status, version number, activity timestamp, deletion fields, and a small set of analysis summaries that are useful for searching and dashboards. Normalizing claim numbers means that entries such as “CA-2024-08-14732” and “ca 2024 08 14732” are treated as the same value during duplicate checks. I also added a writable-field whitelist so the interface cannot overwrite unrelated or system-controlled fields. Required information, valid dates, supported lines of business, allowed statuses, and readiness-score ranges are checked before data is saved.

The new ClaimAnalysis entity keeps the generated report separate from the core claim record. I chose to store the complete report as structured JSON because the report changes depending on which sections the user selects. At the same time, values that may be searched or displayed often, such as confidence level, venue risk, liability allocation, and readiness score, are stored in their own fields. This was one of the main design decisions in the project. Breaking every report section into its own entity would have created a large number of unstable structures and unnecessary joins, while continuing to store everything in ClaimReview would have repeated the original problem. The hybrid design gave me a practical balance between flexibility and organization.

I also created a backward-compatible ClaimReview adapter so I could introduce the new architecture without rewriting the entire application at once. Existing screens can continue using the familiar Base44 entity interface, but the adapter now routes new claims, analysis updates, reads, and deletions through the repository layer. When a report is generated, the adapter creates a versioned ClaimAnalysis record, copies only the most useful summary fields back to ClaimReview, and returns a combined object so the existing report screen still works. It also saves the consolidated claim-file text as a related ClaimDocument record. This approach made the database change substantial without creating unnecessary risk in a large and already working analysis screen.

I made sure the database changes were visible in the application instead of existing only in the code. The Saved Reviews page now uses repository-backed searching and filtering, shows record versions, moves deleted reports into a recycle bin, and allows them to be restored. I also added a Database History page that shows the current record state, the latest analysis version, the number of related documents, and a timeline of events such as creation, updates, status changes, deletion, and restoration. These features make it much easier for an instructor or future employer to understand what the database is doing.

Security and privacy were part of the data design from the beginning of this enhancement. Base44 row-level security still limits records to their creator or an administrator. I also filtered audit metadata so that raw claim narratives, medical timelines, full analysis payloads, follow-up conversations, and other sensitive information are not copied into operational logs. Soft deletion provides accountability and recovery without immediately destroying a record. I would not describe the current application as production-ready for regulated insurance information, but the new design reflects a much stronger security mindset than the original beta version.

To support the enhancement, I created a database test script with 13 assertions. The tests cover claim-number normalization, required fields, invalid statuses, readiness-score limits, controlled writes, removal of sensitive audit data, history-field detection, analysis-update recognition, separation of lifecycle updates from analysis versions, restoration of structured JSON, summary mirroring, and document transformation. I also added a GitHub Actions workflow that installs dependencies, runs the database tests, checks the code with ESLint, completes a production build, and packages both the original and enhanced artifacts. This gave me repeatable proof that the work functioned instead of relying on a statement that I had tested it.

Deployment and End-to-End Verification

After the automated checks passed, I merged the enhancement into the main branch and allowed the updated schemas to synchronize with Base44. I then tested the full workflow inside the deployed application. Base44 recognized the new ClaimAnalysis, ClaimDocument, and ClaimReviewHistory entities. Creating a new claim produced a core ClaimReview record with a normalized claim number, a completed and versioned ClaimAnalysis record, and a related ClaimDocument record that used the same claim_review_id. The history table also captured the claim as it moved through created, status_changed, soft_deleted, and restored events. The screenshots included with the submission show that the design worked in the actual application, not only in automated tests.

Course Outcome Coverage

In Module One, I identified Outcomes 3, 4, and 5 as the main outcomes for this database enhancement. That assessment still fits the completed work, although I narrowed the implementation as the project developed. My original plan mentioned separate structures for users, claims, policies, uploaded documents, reports, and historical information. During development, I kept Base44 authentication for users and left the current policy fields with the main claim record because the application did not yet have a complete policy-management workflow. This was a deliberate scope decision. I preferred to finish a smaller number of meaningful relationships, repositories, lifecycle controls, and tests rather than add several weak entities only to match an early outline.

Outcome 3: Computing Solutions and Design Trade-offs. This work shows meaningful progress because I had to design a solution while balancing several competing needs. I considered how much information should be normalized, which fields needed to remain easy to search, how older records would continue to work, and how to introduce related entities without breaking the current interface. Keeping the variable report body in a ClaimAnalysis JSON payload was a conscious compromise between strict normalization and flexibility. The compatibility adapter was another compromise because it added an extra abstraction layer, but it also reduced migration risk and allowed existing screens and records to continue working.

Outcome 4: Computing Practices That Deliver Industry Value. The enhancement strongly supports this outcome because it applies current computing practices to a problem that has real value in insurance claims operations. I used React, the Base44 SDK, repository modules, entity schemas, automated testing, version control, and GitHub Actions to build and validate the solution. Features such as the recycle bin, history timeline, duplicate-claim checks, analysis versioning, and searchable summaries address practical claims needs, where information must remain organized, understandable, and recoverable throughout the life of a file.

Outcome 5: Security Mindset. The project also shows substantial progress toward this outcome. I limited which fields can be updated, maintained row-level access controls, reduced the amount of sensitive information written to audit logs, separated detailed analysis from operational metadata, and replaced permanent deletion with a recoverable record state. I also accounted for older records that do not contain every new lifecycle field so the migration would not unintentionally block access to existing data. These decisions helped me see security as an ongoing design responsibility rather than a feature added at the end.

The database work also supports Outcome 2 through architecture documentation, automated test results, the visible history page, screenshots, and this narrative. Outcome 1 was not a main focus of this milestone. The pull request, documentation, and reviewable history support professional collaboration practices, but I would not claim that an individual project fully demonstrates creating a collaborative environment for a diverse team.

Reflection on the Enhancement Process

The most important lesson I took from this milestone is that saving data is not the same as designing a database. ClaimIntel already persisted records before I began, so it would have been easy to present that as the database component and stop there. The enhancement pushed me to think more carefully about boundaries, relationships, retrieval rules, record lifecycles, and how to prove that the data remains dependable as the application grows.

One of the hardest parts was introducing the new architecture without breaking the application that was already working. The New Claim Review page and several other components depended on direct Base44 entity calls. Rewriting every screen would have turned this milestone into another broad software-engineering refactor and created many opportunities for regressions. Instead, I separated the raw Base44 client from the application client and routed ClaimReview operations through a compatibility adapter. I had to be careful about recursion because the repository modules needed to use the raw client; otherwise, an adapter call could loop back into itself. Solving that issue gave me a much better understanding of abstraction boundaries and safe migration design.

Supporting old and new records at the same time was another challenge. Existing ClaimReview records still store their analysis in the original fields and do not contain every new lifecycle property. New reports use ClaimAnalysis. To handle both, the read process combines a core claim with the newest related analysis when one exists and falls back to the older record structure when it does not. This helped me understand that a database migration rarely happens all at once. Backward compatibility is part of responsible engineering when users still need access to data during a transition.

I also had to think more carefully about what belongs in an audit log. A claim file may contain medical, financial, legal, and personally identifiable information. Logging the full request or response might make debugging easier, but it would also create an unnecessary privacy risk. I built a sanitization layer that keeps useful operational details while leaving out sensitive fields. That decision reinforced that observability and privacy can work together, but only when the application is intentional about data minimization.

Scope control became another major lesson. My first plan included separate users, claims, policies, documents, reports, audit records, history, indexes, and future comparative intelligence. Trying to build every one of those as a complete subsystem in a single milestone would have made the project broader but less convincing. Base44 also does not expose traditional SQL index and foreign-key configuration through its project schemas. I focused instead on the parts I could build, test, and demonstrate clearly: related entities, normalized identifiers, filtered retrieval, repositories, controlled updates, versioned analysis, audit minimization, record history, deletion and restoration, and automated validation.

The automated checks also gave me a small but valuable reminder about professional quality. The database tests and production build passed, but the lint step caught three unused icon imports in existing components. Those imports had nothing to do with the database design, but leaving the workflow in a failed state would have weakened the credibility of the entire submission. I removed them and ran the same pipeline again until the tests, lint checks, and build all passed together. That experience showed why validation should cover the whole branch, not only the files I expected to affect.

Overall, this enhancement moved ClaimIntel beyond basic record storage and toward a more defensible data architecture. Core claim information is now separated from changing analytical output, related document information is retained, versions and activity are tracked, deleted records can be recovered, database writes are controlled, and sensitive audit content is minimized. Just as important, the process improved how I evaluate trade-offs, work within platform limitations, plan a safe migration, and provide evidence that a solution works. Those are skills I can carry into future work in software engineering, artificial intelligence, and insurance technology.
