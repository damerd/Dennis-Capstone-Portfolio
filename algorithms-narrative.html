Artifact Description

ClaimIntel is an AI-assisted insurance claims intelligence application that I created in 2026 to support the review of complex property and casualty claim files. The application accepts structured claim information and text extracted from uploaded documents, then produces an organized report addressing liability, coverage, damages, venue, exposure, missing information, and recommended next steps. I selected ClaimIntel for my ePortfolio because it connects the technical knowledge I developed throughout the Computer Science program with my professional experience in commercial claims, litigation management, risk evaluation, and claims leadership. It demonstrates my ability to translate a real industry problem into a working computing solution rather than treating software development as an isolated classroom exercise.

Justification for Inclusion and Enhancement

I included this artifact because it shows the progression of my thinking as both a computer science student and an insurance professional. Before the enhancement, ClaimIntel could generate a claim-readiness score and identify some possible field mismatches, but much of that reasoning depended on the language model. I initially viewed the presence of an AI-generated score as evidence of intelligent processing. During the enhancement, I learned that useful output is not the same as a defensible algorithm. If the same claim package can produce different scores, or if I cannot explain how each score was calculated, the system is difficult to audit, test, and trust. That realization changed the purpose of the enhancement from simply adding more validation features to building a repeatable and explainable decision-support process.

The enhanced artifact now uses a deterministic validation pipeline before the generative analysis begins. The system normalizes and tokenizes claim information, builds an inverted document index, compares entered values with indexed evidence, detects unsupported or missing information, removes duplicate issues, ranks findings by severity, and calculates a weighted readiness score. The most important improvement is not the number of new features. It is that the validation result is now reproducible, source-aware, and independently testable. The language model remains useful for narrative analysis, but it no longer controls the authoritative readiness score. This separation taught me to assign AI only the responsibilities it is suited to perform and to keep high-impact scoring logic in transparent code.

Selecting the data structures also became a learning exercise rather than a checklist. I used Sets because the engine needed efficient membership checks and duplicate prevention, Maps because it needed direct relationships between tokens, source documents, rules, weights, and issue identifiers, and a stable max-priority queue because adjusters need the most consequential conflicts surfaced first. Building the inverted index requires additional memory, but it avoids repeatedly scanning the entire document package for every validation rule and makes it possible to trace evidence back to its source. I learned that the correct data structure is determined by the operations and trade-offs of the problem, not by which structure appears most advanced. The index is built in approximately O(T) time, where T is the number of processed tokens, while priority-queue insertion and removal require approximately O(log I) time for I detected issues. Documenting those costs helped me evaluate why the design was appropriate rather than merely showing that it worked.

Course Outcome Coverage

This enhancement demonstrates the strongest progress toward the third Computer Science program outcome: designing and evaluating computing solutions using algorithmic principles while managing design trade-offs. I created an explainable scoring process, selected data structures based on the operations the system performs, considered time and space complexity, and wrote fourteen automated tests covering priority ordering, source mapping, name normalization, line-of-business synonyms, mismatch detection, duplicate prevention, score boundaries, negative evidence, and insufficient-information handling. The tests were especially important because they forced me to evaluate the assumptions behind the algorithm instead of only confirming the expected success path.

The enhancement also supports the fourth outcome because the algorithm addresses an industry-specific need: claims professionals must identify contradictory information, unsupported monetary values, missing documentation, and incomplete investigation before relying on an analysis. It supports the fifth outcome by preventing conflicting form information from being silently accepted, returning an Insufficient Information result when the evidence is inadequate, treating uploaded text as data rather than executable content, and separating deterministic validation from generative output. The in-application validation preview and technical documentation also support the second outcome by explaining the result to both technical and nontechnical audiences. My Module One outcome plan did not materially change, but the completed enhancement provided stronger evidence than I initially anticipated. I planned to demonstrate centralized validation, conflict detection, readiness processing, and reusable utilities; the final work also demonstrates source indexing, priority-based processing, weighted scoring, complexity analysis, and regression testing.

Reflection on the Enhancement Process

The most important learning occurred when the first version of the new engine failed in ways that initially appeared reasonable. For example, it marked an optional form field as missing even when the uploaded claim document clearly contained the information. That exposed a flaw in my own assumptions: I had treated the form as the primary source of truth even though ClaimIntel is designed to analyze a complete claim package. I revised the logic so the system checks both structured fields and indexed document evidence, then added a regression test. This experience reinforced that an algorithm can be internally consistent and still be wrong because its rules do not accurately represent the real-world problem.

A second challenge involved the difference between the presence of a word and the presence of supporting evidence. A file stating that no demand had been received still contained the word demand, but that did not establish an actual settlement demand. Direct substring matching could not represent that distinction. I narrowed the evidence phrases, added logic for negative demand language, and created a specific test for the edge case. I made a similar correction to monetary matching after recognizing that concatenating all digits from every document could create false matches across unrelated values. These problems taught me that text processing is not just a search problem; it requires careful definitions of context, support, and contradiction.

The testing process also changed how I evaluated progress. My first instinct was to judge the enhancement by whether the interface displayed a score and warning message. The automated tests showed that visible output is weak evidence of correctness. Testing equal-priority ordering, duplicate identifiers, score limits, conflicting jurisdictions, negative evidence, and short input revealed logical weaknesses that would not have been obvious during a normal demonstration. I learned to treat failed tests as design feedback rather than as obstacles to completing the assignment. Each failure forced me to make the rules clearer and the behavior more predictable.

This enhancement also made me more aware of the risk created by my own professional expertise. Because I understand insurance claims, it is easy to assume that a rule is obvious or universally applicable. Translating that knowledge into software required me to state assumptions explicitly, decide which evidence was sufficient, and recognize where a deterministic rule should stop rather than pretend to understand more than it does. ClaimIntel's validation engine is substantially more transparent and reliable than the original implementation, but it remains a rules-based system rather than a complete natural-language understanding system. The larger lesson is that professional-quality software is not created by adding complexity; it is created by making decisions explainable, testable, and appropriate to the limits of the system.
